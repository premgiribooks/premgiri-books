## Microservice Code Standards

### One Service, One Database Schema

Each microservice has its own Prisma schema file:
```
services/
  auth-service/prisma/schema.prisma        (users, sessions, roles, permissions)
  company-service/prisma/schema.prisma     (companies, branches, financial years)
  masters-service/prisma/schema.prisma     (customers, products, suppliers...)
  sales-service/prisma/schema.prisma       (invoices, orders, challans...)
  ...
```

A service **never** imports or queries another service's Prisma schema. Cross-domain
reads use gRPC calls to the owning service.

---

### Service Interface Contract

Every microservice exposes its public API via:
1. An OpenAPI 3.1 spec (`openapi.yaml`) — REST endpoints
2. A Protobuf definition (`service.proto`) — gRPC endpoints (internal only)

These files are the contract. Changes that break the contract require a version bump
(`/v2/` prefix on the REST path, new proto message version).

---

### gRPC Internal Communication

Services call each other via gRPC on the cluster-internal network:
```typescript
// Never:
const result = await fetch(`http://masters-service/customers/${id}`)

// Always:
const result = await masterGrpcClient.getCustomer({ id, companyId })
```

gRPC clients are generated from Protobuf definitions. No hand-written fetch() calls
between services.

### Kafka Producer / Consumer Standards

**Producer** (any service that emits events):
```typescript
await kafkaProducer.send({
  topic: 'premgiri.sales.invoice.posted',
  messages: [{
    key: companyId,            // partition by company
    value: JSON.stringify({
      eventId: uuid(),
      eventType: 'INVOICE_POSTED',
      companyId,
      invoiceId,
      timestamp: new Date().toISOString(),
      payload: { /* relevant fields only, no full entity */ }
    })
  }]
})
```

**Consumer** (any service that reacts to events):
```typescript
// Must be idempotent — the same event may be delivered more than once
await kafkaConsumer.run({
  eachMessage: async ({ message }) => {
    const event = JSON.parse(message.value.toString())
    if (await isAlreadyProcessed(event.eventId)) return // idempotency check
    await processEvent(event)
    await markProcessed(event.eventId)
  }
})
```

Rules:
- Every consumer must be idempotent (process event twice = same result as once)
- Failed messages go to DLQ after 3 retries (exponential backoff: 1s, 5s, 30s)
- Event payload contains only the minimum fields needed — never full entities
- `eventId` is a UUID generated by the producer — used for idempotency deduplication

### Redis Standards

```typescript
// All cache operations through the CacheService abstraction:
class CacheService {
  async get<T>(key: string): Promise<T | null>
  async set<T>(key: string, value: T, ttlSeconds: number): Promise<void>
  async del(key: string): Promise<void>
  async invalidateNamespace(namespace: string): Promise<void>
}

// Key format: premgiri:{companyId}:{domain}:{identifier}
const key = cacheKeys.productCatalog(companyId, productId)
// → "premgiri:abc123:masters:product:xyz789"
```

When Redis is disabled (Super Admin toggle), `CacheService` is replaced by
`NullCacheService` which returns `null` for every `get()` — callers always handle
cache misses gracefully by fetching from DB.

### Observability Standards

Every service must instrument:
```typescript
// Metrics (Prometheus)
httpRequestDurationMs.observe({ method, path, status }, durationMs)
kafkaMessagesProcessed.inc({ topic, result: 'success' | 'error' })

// Distributed tracing (OpenTelemetry → Jaeger)
const span = tracer.startSpan('postSalesInvoice')
span.setAttributes({ companyId, invoiceId })
// ... operation
span.end()

// Structured logging (Pino → Loki)
logger.info({ companyId, invoiceId, durationMs }, 'Sales invoice posted')
```

Every log line must include: `service`, `companyId` (when in a company context),
`traceId`, `spanId`, `level`, `timestamp`.

### Health Probe Standards

Every K8s pod must implement:
```typescript
// GET /health/live — liveness: is the process alive?
app.get('/health/live', (req, res) => res.json({ status: 'ok' }))

// GET /health/ready — readiness: can the pod receive traffic?
app.get('/health/ready', async (req, res) => {
  const dbOk = await checkDatabaseConnection()
  const kafkaOk = await checkKafkaConnection()
  if (!dbOk || !kafkaOk) return res.status(503).json({ status: 'not ready' })
  res.json({ status: 'ok' })
})

// GET /health/startup — startup: has the pod finished initializing?
app.get('/health/startup', async (req, res) => {
  const migrationsOk = await checkMigrationsApplied()
  res.status(migrationsOk ? 200 : 503).json({ status: migrationsOk ? 'ok' : 'migrating' })
})
```

### Container Standards

Every Dockerfile must:
1. Use a multi-stage build (build stage + production stage)
2. Use a non-root user in the final stage
3. Copy only the built artifacts — never `COPY . .` in production stage
4. Pin the base image to a specific digest (`node:20-alpine@sha256:...`)
5. Set `NODE_ENV=production` in the production stage

---

### Secret Standards

Secrets are never in:
- `docker-compose.yml` values
- K8s ConfigMap
- `.env` files committed to git
- Container environment variables set in the Deployment YAML directly

Secrets are always:
- Stored in HashiCorp Vault
- Injected via Vault Agent Sidecar or the Vault Secrets Operator at pod startup
- Referenced in K8s Deployment as `secretKeyRef` pointing to a K8s Secret
  that Vault populates

## Testing Standards (v4 Amendments)

- Every microservice must have contract tests (Pact / OpenAPI schema validation)
  verifying its API contract matches the spec.
- Kafka consumer handlers must have integration tests using `testcontainers`
  (real Kafka + real DB in a Docker container — no mocks for data-layer tests).
- Redis toggle: every cache-path code must have a test for both Redis-enabled and
  Redis-disabled modes.
- K8s manifests are validated with `kubectl dry-run=client` and `kubeval` in CI.
- Helm charts are tested with `helm lint` and `helm template` in CI.
